## 1. The headline: exact execution-gas equality

Test 1 asserts that a successful transfer, an over-budget transfer, and an insufficient-balance transfer cost **exactly the same to execute**.

```
    indistinguishability:
      path             total gas   calldata gas   zero bytes   EXECUTION gas
      success            713167           3100          131          710067
      over-budget        713143           3076          133          710067
      short-balance      713167           3100          131          710067
```

**710,067 on every path.** Repeated across three independent runs, nine measurements, no variation.

### A correction to what was reported earlier

An earlier draft of this test asserted equality of **total** `gasUsed` and reported "713,134 on all three paths". That number was real but the assertion was measuring the wrong thing, and its passing was luck.

`gasUsed` includes intrinsic calldata cost — 4 gas per zero byte, 16 per non-zero. The caller supplies a fresh encrypted handle and input proof on every call, and the zero-byte count of that ciphertext varies at random. In the run above it is 131, 133, 131, which moves total gas by 24. Three random ciphertexts happening to share a zero-byte count is not rare enough to notice, so the total-gas assertion passed twice and then failed on an unrelated edit, which is what surfaced it.

The attribution is now computed inline and printed, and the test asserts two things:

- execution gas (`gasUsed` minus intrinsic calldata) is identical across the three paths;
- the attribution **closes** — every path's `total − calldata` equals the same execution figure, so a future execution-side leak cannot hide behind "it's just calldata".

**Execution equality is the stronger claim, and it is the correct one.** Calldata entropy is generated by the session client before the contract runs; it cannot depend on whether the budget will be exceeded, so it carries no information about the outcome. What an observer could learn from is what the contract _does_, and that is identical.

**Why it holds, structurally.** No path branches on an encrypted value, because none can. An over-budget request still performs a real `confidentialTransferFrom`, with an encrypted zero. `FHE.select` and `FHE.add` mint a fresh handle on every path regardless of the encrypted condition, so `_remaining` is always written with a value that differs from what was there, and the same-value SSTORE discount never applies on any path.

**What the measurement covers.** These figures come from `@fhevm/hardhat-plugin` mock mode. The ACL and the FHEVM executor really are deployed to the local chain and really execute — `ZamaConfig._getLocalConfig` exists precisely because chainid 31337 has its own host contracts — so the ACL storage writes and executor calls are real EVM work. What is mocked is the FHE computation itself. The equality argument is about the operation sequence rather than the cost of any single operation, so mock mode is the right place to assert it. **Confirming the same equality on Sepolia remains an open item for step 5.**

### The accepted gate criterion

Criterion (b) from `step3-gate.md` §5 is the accepted gate, and `spikes/sepolia-equality.ts` enforces it:

- **hard equality** on the FHE operation sequence, across every path;
- **hard equality** on HCU, across every path;
- **execution gas** bounded at a 4 gas spread, with the per-path distributions required to be statistically indistinguishable — chi-square against the critical value at p = 0.05 — and the calldata attribution required to close on every sample.

It passes on 60 live Sepolia transactions, 20 per path: one operation sequence, one HCU value, chi-square 2.927 against a critical 5.991. The residual leak is bounded and written up in `docs/leakage.md`.

The original criterion — execution gas exactly equal — is falsified on chain and cannot be satisfied by any change to this contract, because the 4 gas lives in `HCULimit`'s own accounting. Criterion (b) asserts hard equality exactly where the claim lives and bounds the rest rather than waving at it.

**Sepolia, 2026-08-27.** The confirmation run happened, before any SDK code. Full report in `docs/step3-gate.md`. Summary: across 22 live transactions the FHE operation sequence and the HCU consumption are **identical** on every path — and HCU came out at exactly the 1,334,064 analytic estimate below. Execution gas is **not** constant: it takes two values four gas apart. That variance is intra-path — ten sends on one fixed path produced both values — and a trace localises it to a single `HCULimit.checkHCUForFheGe` call, outside GhostKeySession, the token and the ACL, all three of which are bit-identical between the two values. It is uncorrelated with the outcome and no change to this contract could remove it. The gate criterion is under review; see `step3-gate.md` §5.

Test 1's setup is deliberately symmetric: three separate owners, three separate session keys, and a recipient warmed beforehand so `_balances[to]` is initialized on every path. Every storage slot each path touches is cold in the same way.

## 2. Two real bugs the tests caught

### 2.1 The emitted handles were undecryptable

The design review had C2 right in principle and wrong in practice.

The plan was to emit `within` and `sent` with `FHE.allow` to the owner and the session key, so a client could tell a budget rejection from an insufficient balance. That was implemented, and tests 3 and 3b failed with:

```
dapp contract 0xB7f8... is not authorized to user decrypt handle 0x00d9ba4a...
```

`userDecrypt` authorises against **both** the requesting account and the contract the handle is read through. The module held only _transient_ access to `within` and `sent` — granted by the executor for `within`, by the token for `sent` — and transient access dies at end of transaction. Granting the two reader accounts was not enough; the module had to grant itself persistently as well.

Fix: `FHE.allowThis(within)` and `FHE.allowThis(sent)` before the per-account grants.

Without those two lines the contract compiles, every budget test passes, and the emitted handles are permanently undecryptable — the two-failure-mode distinction, which is the entire reason C2 exists, would have been silently dead. Caught only because tests 3 and 3b decrypt the event fields rather than just checking the budget.

### 2.2 The gas assertion was measuring the wrong quantity

See §1. Caught by an unrelated edit making the flap visible, then diagnosed by attribution rather than by adjusting the assertion until it passed.

## 3. Design decisions taken

**`closeSession` does not zero the budgets.** The plaintext guards in `send` already reject every call once `expiry` is 0, and a session key can never be reused, so a stale budget handle is unreachable. Zeroing would cost one FHE operation and one storage write per funded token on a function that must stay cheap and unconditional — the session client has to be able to self-terminate even under gas pressure. Leaving the handle also keeps the final balance auditable by the owner afterwards.

**A zero amount is rejected client-side, not on chain.** `requested == 0` produces `within = true, sent = 0`, identical to an insufficient balance. Distinguishing them on chain would cost an extra FHE operation for no benefit: the session client constructed the ciphertext and knows its own plaintext. The natspec states this as a client obligation.

**`Session` packs into one slot** via sentinels rather than flags: `owner == 0` means never used, `expiry == 0` means closed, `expiry <= block.timestamp` means lapsed. `owner` is never cleared, which makes the single-use key invariant structural. Test 8c pins it.

**No token allowlist as separate state.** `FHE.isInitialized(_remaining[key][token])` is the guard — the same check a separate allowlist would perform, without the extra storage.

**The recipient allowlist is a one-based index map, not a bool map.** Zero means "not allowed", which doubles as the membership test, and the index is what makes `removeRecipient` a swap-and-pop instead of a linear scan. One mapping instead of two.

**`increaseBudget` does not trust `tryAdd`'s failure value.** `FHESafeMath.tryAdd` returns zero on overflow, which would erase the budget. The old value is reinstated explicitly with `FHE.select(ok, sum, current)`.

## 4. Amendments A1–A4

**A1 — token guard.** `require(FHE.isInitialized(_remaining[msg.sender][token]))` before the external call. An uninitialized budget prevents _spending_ but not _calling_, and `send` grants the token transient ACL access via `FHE.allowTransient(amount, token)` immediately before invoking it. Without the guard, a compromised session key could name any address and get both an ACL grant and a call to it. `isInitialized` is a pure zero-check (`FHE.sol:90-92`), so it costs no HCU. Test A1. `nonReentrant` is kept as well — the guard eliminates arbitrary contracts, the reentrancy guard covers a hostile token the user registered themselves.

**A2 — exact gas equality.** Done, §1, on execution gas.

**A3 — terminology.** `session client` and `model` throughout the interface and contract natspec. The word "agent" appears nowhere on its own. Defined once at the top of `IGhostKeySession`.

**A4 — multi-token `openSession` in one transaction.** `SessionParams` carries parallel `tokens` and `budgets` arrays under a single shared `inputProof`. Test 5 confirms the SDK side: one `createEncryptedInput` with two `add64` calls yields `handles.length === 2` under one proof, both budgets funded in one transaction. `FHE.fromExternal` consumes **no HCU** (no `checkHCUFor*` entry for `verifyCiphertext` in `HCULimit.sol`), so the ceiling is calldata and EVM gas. Capped at `MAX_TOKENS = 32`. Duplicates rejected with `DuplicateToken`.

## 5. Amendments B1–B4

**B1 — session key consent, closing the front-running grief.** `openSession` now requires an EIP-712 signature from the session key. Without it, anyone watching the mempool could resubmit a pending open with the same key and more gas, become owner, and make the honest call revert with `SessionKeyAlreadyUsed` — permanently burning the key, since the single-use invariant never clears `owner`. No funds at risk, but every session open was grievable for the price of gas, and a live demo would have been trivially disruptable.

`chainId` and `verifyingContract` are bound through the **EIP-712 domain separator** rather than as struct fields. That is the standard place for them and it is what the brief's replay requirement asks for; adding them to the struct as well would be redundant. Tests B1d and B1e prove both bindings hold. No nonce is needed: a key is single-use, so a replayed signature meets `SessionKeyAlreadyUsed` on the second attempt.

`openSessionDigest` is exposed as a view so the SDK signs exactly what the contract verifies; test B1f asserts the two agree by recovering from the on-chain digest.

Six tests: valid open, front-runner replaying the honest signature, wrong signer, wrong chainId, wrong deployment, digest agreement. B1b also asserts the key survives the failed attack and the honest open still succeeds.

**B2 — the premise was wrong; the gap was real.** The amendment stated that `protocolStatus` hardcodes the Ethereum mainnet ACL and would revert on Sepolia. It does not. `ZamaConfig.getEthereumCoprocessorConfig()` dispatches on chainid across mainnet (1), Sepolia (11155111) and local (31337) — "Ethereum" names the network family, not mainnet — and it is the **same function** `ZamaEthereumConfig`'s constructor calls, so this view cannot disagree with the config the contract runs on.

What was correct is that **no test touched `protocolStatus` at all**, which is exactly why nobody could be sure. Test B2 now calls it and asserts sane values; it passes on the local chain, exercising the 31337 branch. The natspec now records why the name is misleading so the same doubt does not recur. No other config access in the contract resolves an address independently.

**B3 — `addRecipient` / `removeRecipient`.** `_allowed` was only written at `openSession`, so a new payee mid-session required an entirely new session: new key, new ACL delegation, new batch signature. That breaks "authorize once, talk all day".

`addRecipient` is owner-only; `removeRecipient` is owner **or** session key, so the client can narrow its own scope defensively rather than choosing between carrying on and tearing the session down. Neither grants authority the owner did not already have — closing and reopening achieves the same thing — it is the same authority at a far lower cost. Both emit events. Six tests, including B3e which walks add / remove-from-the-middle / remove-the-moved-element / re-add to pin the swap-and-pop index fixup.

**B4 — minor guards.** `increaseBudget` now rejects a lapsed session (`expiry <= block.timestamp`), which previously let an owner top up into an unusable state and believe it worked. `MAX_TOKENS = 32` and `MAX_RECIPIENTS = 128` bound the arrays that `tokensOf` and `recipientsOf` return whole, so a session cannot make its own views uncallable. The recipient cap is enforced in `addRecipient` too, so it cannot be walked past one at a time.

## 6. HCU: estimated vs measured

Analytic estimate, unchanged by implementation:

| side            | operations                                                              | HCU           |
| --------------- | ----------------------------------------------------------------------- | ------------- |
| module          | `tryDecrease` 369,000 + `select` 55,000 + `sub` 162,000 + `add` 162,000 | 748,000       |
| token `_update` | `tryDecrease` 369,000 + `select` 55,000 + `add` 162,000                 | 586,000       |
| both            | `trivialEncrypt` × 2                                                    | 64            |
| **total**       |                                                                         | **1,334,064** |

6.7% of the 20,000,000 per-transaction ceiling; roughly six operations of sequential depth against the 5,000,000 depth limit.

**Not measured.** Mock mode does not meter HCU in a way the test can read back, so test 10 asserts on the operation shape via EVM gas and the HCU figure remains analytic. Measuring real HCU on Sepolia is an open item for step 5.

The B1 signature check adds one `ecrecover` (~3,000 gas) to `openSession` and nothing to `send`. `FHE.allowThis` and `FHE.allow` are ACL writes, not FHE operations: EVM gas, no HCU.

## 8. Open questions for step 3

1. **Sepolia confirmation of execution-gas equality and HCU.** The structural argument is sound and mock mode agrees across nine measurements, but the headline claim deserves live evidence. Needs three funded owner EOAs.
2. **The SDK must sign the open.** `openSession` now takes a session-key signature. The SDK should call `openSessionDigest` and sign it rather than reconstructing the EIP-712 payload independently — test B1f exists to catch a drift between the two, but only if the SDK uses the view.
3. **Zero-amount rejection is a client obligation.** The contract deliberately does not spend an FHE op on it. If the SDK forgets, users get told "insufficient balance" when they asked to send nothing.
4. **`within` is an `ebool`.** Decrypted with `FhevmType.ebool`, a different call from the `euint64` handles. Two decrypt paths in one result object.
5. **Delegation is optional and the SDK must model it as such.** ACL delegation is required for exactly one capability: reading the holder's _balance_, needed only for reference amounts like "send half". What was spent, what remains, and what actually moved are all readable from this module's own handles with no delegation. The tier to expose: _the session client sees what it spent and what remains, but not what is in the wallet._
6. **`protocolStatus` belongs in the client's error path.** `send` never reverts on a budget or balance failure, but it can still revert because the ACL is paused or has deny-listed a participant.
7. **Operator expiry is not tracked here.** `token.setOperator(module, expiry)` is set outside the session and can lapse independently of `Session.expiry`. A session whose operator grant has expired reverts inside the token rather than failing gracefully. The SDK should check both, or step 3 should decide whether the contract exposes a combined readiness view.
