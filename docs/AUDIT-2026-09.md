# SaveTogether — design audit, September 2026

Four agents read the project in parallel along different axes: frontend and product,
PoolTogether V5 mechanism gaps, unused Zama / ERC-7984 capability, and narrative and
evidence. This file is their findings in one place, re-checked.

**Not a code audit.** Nothing here is about style, structure or refactoring. It is
about what the design gets right, what it gets wrong, what is missing, and — a
category worth as much as the others — what should deliberately *not* be built.

## How to read the verification marks

| mark | meaning |
|---|---|
| **[V]** | **Verified in this session.** I ran the check myself; the command or the file:line is named. |
| **[R]** | **Reported.** An agent's finding, plausible and specifically cited, not independently re-run. |
| **[D]** | **Disputed.** Two agents disagreed. The disagreement and its resolution are stated rather than smoothed over. |

Where a finding contradicts something the repo currently says, the repo's line is quoted.
An agent asserting something is not evidence; several of the sharpest claims below
survived checking and a few did not.

# Part 0 — Act first

Five items. The first is live and extractable, the second is a false vulnerability
report we published about ourselves, and the third has a clock on it.

## 0.1 [V] `accrueMany` pays a fee for doing no work — profitable, permissionless, live

`accrue` early-returns on an address already accrued for that draw:

```solidity
// ConfidentialPrizePool.sol:866
if (accrued[drawId][user]) return;
```

`accrueMany` then pays for the *length of the array*, not for work performed:

```solidity
// ConfidentialPrizePool.sol
for (uint256 i = 0; i < n; i++) accrue(order[i], drawId);
_payKeeper(drawId, n);          // n = users.length

function _payKeeper(uint32 drawId, uint256 count) private {
    if (keeperFee == 0 || count == 0) return;   // only checks the array is non-empty
    ...
    asset.confidentialTransfer(msg.sender, paid);   // <-- to the caller
}
```

`accrueMany` is `external` with no modifier, and the fee goes to `msg.sender`.
So **anyone may call `accrueMany([alreadyAccruedAddress], someDrawId)` and be paid
`keeperFee` for an accrual that early-returned.**

Verified on the deployed pool: `keeperFee()` returns `200000` = **0.2 cUSDC**, against
tier prizes of 25 / 5 / 1 cUSDC. Roughly 125 repeat calls drain a grand prize out of
the reserve, each costing the caller a fraction of a cent of Sepolia gas. It is
bounded only by `tryDecrease` declining once the pot is empty — at which point real
prizes stop being payable too, so the drain ends by breaking the thing it drains.

Even with no attacker it inverts the honest keeper's incentive: accruing six users in
six calls earns six times what accruing them in one call earns.

**It is also unpinned by any test.** The B4 suite in `test/phase-b.ts` has two cases —
one `accrueMany([alice], 1)` asserting the fee is paid, and one asserting the fee is
declined when it would displace a prize. Neither calls `accrueMany` twice with an
already-accrued user, so both would pass unchanged if the guard were added. The
regression test is one call repeated: assert the caller's balance moves once, not twice.

**Fix.** Have  return whether it did work, count the trues, and pass that count
to `_payKeeper`. Two lines, no FHE cost. PoolTogether V5 does not have this shape —
`startDraw` / `finishDraw` revert if already called for a draw, and rewards are per
auction rather than per array element.

## 0.2 [V] We publish a false critical-vulnerability report about our own contract

`docs/inventory.md:90`, in bold:

> **`ConfidentialPrizePool` has no access control of any kind.**

and `:94`:

> ### `setYieldSource` (:538) — a live drain path

The contract has **five** `onlyOwner` sites (`:294` defines the modifier; `:727`,
`:769`, `:797`, `:810` apply it). The document is dated 31 August 2026 and was true
then. It is linked from `README.md:662` and from the live site's Rubric screen.

A reviewer following our own link finds a formatted drain-path report on the headline
contract and will believe the document over the code, because we published it. This is
the single worst item in the package and it is a one-line fix.

## 0.3 [V] The keeper runs out of gas in about two days

Read from chain during this audit:

```
keeper 0xF505e2E7…E5Ae balance : 0.480321 ETH
measured burn per draw          : 0.005915 ETH   (bundle/STATE-NOW.md §6)
draws remaining                 : 81
at the observed ~41m cadence    : 55.5 hours  ≈  2.3 days
```

`README.md:1007` says *"roughly 1.5M gas… at 2 gwei that is ~0.003 ETH"* — about half
the measured figure, and smaller than a single `accrueMany(6)` transaction. The
project's own measurement (0.005915) is used correctly in `docs/leakage.md` §7; only
the README's operator section is optimistic.

When it empties, `openDraw` stops, the current draw stays Open, and **every later draw
is blocked behind it**. `README.md:1010` describes this failure mode correctly; nothing
in the product surfaces the runway. Note the pool is already overdue by several hours
as of this audit.

**Fix, in order:** top the keeper up; correct `:1007` to the measured number; put
"keeper balance / draws of runway" on the Verify screen, where it is a public fact
about a permissionless function anyone may call.

## 0.4 [V] The agent's pool position belongs to the session key, not to you

`packages/sdk/src/pool.ts:119` uses `this.ctx.sessionKeyAddress` as the depositor of
record, and the contract pays whoever asks:

```solidity
// ConfidentialPrizePool.sol:348
function withdraw(externalEuint64 encAmount, bytes calldata inputProof) external {
    _drain(msg.sender);
    euint64 balance = _balanceOf(_userObs[msg.sender]);
```

The session key is a full EOA. A leaked key withdraws the entire accumulated pool
position and sends it anywhere. That contradicts the bound in `docs/architecture.md:100`:

> A leak costs at most the remaining encrypted budget, to addresses already on the
> allowlist, until expiry.

True of the *model*, which has no tool to move the session key's own tokens
off-allowlist. **Not true of the key.** The owner additionally cannot read the position
— no `delegateForUserDecryption` is granted for the pool address, only per token.

**Fix, best first:** deposit through `confidentialTransferFromAndCall(owner, pool, …)`
so the pool credits `from` — the owner keeps the position and withdrawal authority
while the session key keeps deposit-only authority, which is the correct capability
split for an agent rather than a limitation. Interim: have the session key call
`IACL.delegateForUserDecryption(owner, poolAddress, expiry)` at open, so the owner can
at least see what the agent holds.

## 0.5 [V] Every yield source ever configured keeps an unlimited, permanent operator grant

```solidity
function setYieldSource(IYieldSource source) external onlyOwner {
    yieldSource = source;
    if (address(source) != address(0)) {
        asset.setOperator(address(source), type(uint48).max);
    }
    emit YieldSourceSet(address(source));
}
```

The previous source is never revoked. `type(uint48).max` is unlimited amount and no
expiry over the pool's entire cUSDC balance. Owner-gated, so it takes an owner action
to create a stale grant — but once created it is permanent and invisible.

**Fix.** `asset.setOperator(oldSource, 0)` before rebinding, and a bounded `until`
instead of `type(uint48).max`. The contract already calls that function.

# Part 1 — The frontend, verified

Six findings I re-checked myself. Ordered by how much they cost a real visitor.

## 1.1 [V] The odds and the deposit quote go blank for most of every cycle

`openDraw` writes the aggregate as zero and only `revealDraw` fills it:

```solidity
_draws[drawId] = Draw({ …, totalWeight: 0 });
```

`Pool.tsx` divides by it, reading the **latest** draw:

```ts
const total = window > 0 ? Number(d.totalWeight) / window : 0;
if (total <= 0 || raw === undefined) return null;
```

So while a draw is Open — the majority of a ~41-minute cycle — `myOdds`, the exact
per-round odds panel, and the "if you deposit N more" quote all return `null` and
disappear. **The quote vanishes precisely while someone is typing an amount into the
deposit box.**

`Position.tsx:203` already solves this correctly with `draws.find(d => d.revealed)`.
Two screens answer the same question and the one where money is committed is the one
that goes dark. The fix is one `.find` against draws `Pool.tsx` already multicalls for
the countdown estimate.

## 1.2 [V] Verify announces wins the contract may never have paid

`Verify.tsx` renders, in green:

```tsx
{cleared === null ? "•••" : cleared ? `WON ${Number(prizes[t] ?? 0n) / 1e6} cUSDC` : "not cleared"}
```

from a purely local `myWeight > threshold` comparison. But a cleared threshold against
an underfunded reserve credits **zero**:

```solidity
(ebool funded, euint64 nextReserve) = FHESafeMath.tryDecrease(_reserve, credit);
euint64 paid = FHE.select(funded, credit, FHE.asEuint64(0));
```

`Verify.tsx` mentions the reserve **zero times** (grep count: 0). `Position.tsx` says
*"Cleared is not the same as paid"* exactly once. The two screens disagree about the
same fact and the louder, greener, more confident one is wrong. Measured shortfall
frequency is 3.2–3.6% per configuration, and 97.3% on the first draw.

## 1.3 [V] Revoking a session leaves the credential live on screen

`Chat.tsx` `revoke()` sends the on-chain calls and refreshes status. It never clears
`token`, `mcpUrl`, or `localStorage` (grep for `setToken|removeItem|setMcpUrl` inside
the function: **0 hits**).

After revoking: the connector URL is still displayed, **the Copy button is still active
on a dead credential**, the spend-capable token is still on disk, and the "open a
session" form is gone because it renders on `mcpUrl === null`. There is no way back
short of clearing site data.

## 1.4 [V] `keeperFee()` is in the ABI and read by nothing

Grep across `frontend/app` and `frontend/components` for `keeperFee`: **0 hits.** It is
the only cost the protocol charges a depositor, it is paid from the same reserve the
prizes come from — so it competes directly with prizes for a pot that can run short —
and no screen mentions it.

## 1.5 [V] One media query in the whole application

Grep for `@media|matchMedia|innerWidth` across `frontend/{app,components,lib}`:
**1 hit**, in `globals.css`, adjusting `main` padding and three class names of which
only one is still used.

The shell is a bare flex row with a `264px` fixed sidebar. At 375px that leaves about
**61px** for every screen — the deposit input, the odds table, the threshold table and
the Break output all render into that column. The app is a desktop demo.

## 1.6 [R] The Break screen claims five live attacks and runs two

`Break.tsx` header: *"Five attempts against the live pool, run with your own wallet…
Nothing here is staged."* Rows 3 and 4 are hard-coded JSX — a static table of two
hashes and two literal `<Out>` blocks. Row 5 runs a local binary search against a
number the visitor types, using a copied `coarsenBudget`, and never touches the server.
The page's own banner concedes it: *"Connect to Sepolia to run rows 1 and 2. Rows 3, 4
and 5 work regardless."*

Rows 3–5 are legitimate *evidence*. Presenting cited evidence in the same visual
grammar as live execution, under a headline that says nothing is staged, is the one
failure `README.md:868` says would be worse than not having the screen.

Row 3 is two `eth_getTransactionReceipt` calls from being real, and it is the row the
deck calls THE PROOF.

## 1.7 [R] Other frontend findings worth acting on

- **The public audit is gated behind a wallet, a signature and a paid transaction** on
  the screen that says *"anyone can compute them, for any address, in any draw."* The
  entire audit UI sits inside a `myWeightHandle !== null` branch fed by an on-chain
  `weightFor` write. The draw selector lives *inside* that branch and its `onChange`
  clears the handle — so the control destroys the panel containing it. The default
  target is the latest draw, which is usually Open and therefore not auditable, so the
  first transaction a visitor pays for is guaranteed to fail.
- **Requiring a transaction to check your own result reintroduces the signal the
  protocol was restructured to delete.** `docs/leakage.md:107` states the rule:
  *"no one has to transact merely to learn whether they won."* Whoever sends
  `weightFor(N, self)` minutes after draw N reveals is observably checking a result.
- **`Rubric.tsx` is 315 lines, has an icon, a route and a case — and no sidebar entry.**
  Vault's retirement is deliberate and documented; Rubric's is neither shipped nor
  removed.
- **Position's counts are silently windowed** to the last 12 draws and rendered without
  saying so, on the screen whose premise is that every figure is honestly derived.
- **Six different labels for the same EIP-712 signature** across six screens, at four
  different contract scopes, and nothing tells a user which permits they already hold.
- **The 7% APY headline carries no caveat** at 34px; the correction ("the rate is ours,
  Zama's vault is idle-only") is far below the fold. `README.md:723` makes "every screen
  that shows it says so" an obligation.

## 1.8 The single highest-value frontend change

**Delete the `weightFor` transaction from Verify, compute the weight locally with
`lib/twab.ts`, and ungate the audit UI.**

It is exact, not an approximation: `weightForWindow` computes
`cumulativeAt(snapshotAt) − cumulativeAt(periodStart)`, and the contract's own comment
at `:925` explains why its cached branch is equivalent — *"for a Revealed predecessor
`periodStart` IS its snapshot."*

Five problems collapse into it: the screen's headline claim becomes true for a
disconnected visitor, the reset loop disappears, the dead-end first transaction
disappears, gas leaves the audit path, and a winner-correlated on-chain signal leaves
the screen whose entire purpose is disproving leakage. `lib/twab.ts` already powers
Position, and its docstring anticipated exactly this substitution.

# Part 2 — Mechanism: what PoolTogether V5 has that we do not

38 V5 mechanisms were enumerated against ours. Most absences are correct and already
argued. Four are genuine gaps, and three of our stated impossibilities do not hold.

## 2.1 [D] Floating prize sizes — the two agents contradicted each other, and both were half right

This is the most valuable disagreement the audit produced, so it is written out rather
than resolved silently.

**The Zama agent said** V5's shape cannot be ported: V5 computes
`prize = tier liquidity / prize count`, the natural denominator here is the *realised
winner count* which is encrypted, and `FHE.div(euint64, euint64)` does not exist —
therefore "not merely unbuilt; it is not expressible."

**The PoolTogether agent said** the blocker is overstated: the divisor can be a
plaintext constant, and scalar division is exactly the supported form.

**[V] Both checked against the pinned library.** `node_modules/@fhevm/solidity/lib/FHE.sol`:

```
6566:    function div(euint64 a, uint64 b) internal returns (euint64) {
```

`div(euint64, euint64)` does not exist. So:

- **V5's literal mechanism is not expressible.** Dividing by the number of winners that
  actually occurred needs an encrypted denominator. The Zama agent is right that this
  roadmap item, as worded in `docs/tier-derivation.md` §4 ("prize = tier liquidity /
  winner count"), cannot be built.
- **A fixed-plaintext-divisor variant is expressible and gets most of the value.**
  `prize_t = FHE.div(_reserve, C_t)` with `C_t` a published plaintext constant is the
  supported form, computed **once per draw** rather than per accrual: three divisions at
  715,000 HCU = ~2.1M against a 20M per-transaction ceiling, depth 715,000 against a 5M
  limit. Per-accrual cost is unchanged, because `FHE.select(won, encPrize, credit)` costs
  the same 55,000 as selecting a plaintext constant.

**What the variant buys.** It closes the top item on the README's "what is not done"
list, removes the owner's power to rewrite payouts mid-flight, and restores the grand
prize's *growth* — today it pays 25 cUSDC whether it fires on draw 3 or draw 300, which
is the actual appeal of a grand prize and we do not have it.

**It also reduces leakage.** `docs/leakage.md` §3's inference is
`delta totalWeight = winners x prize` against known prizes 25/5/1, which usually
decomposes uniquely. With encrypted per-draw-varying prizes the equation gains unknowns
and the tier decomposition stops being solvable.

**Honest caveat.** With one pot, N simultaneous winners still draw N x prize, so the
clamp is not eliminated. Sizing `C_0 >= 4` makes the *first* clamp impossible by
construction, which covers the 97.3% first-draw case and most of the 3.2–3.6%. Full
per-tier isolation needs per-tier pots, measured in-repo at 2,229,000 vs 615,000 HCU per
accrual — and that measurement was taken *with fixed prizes*, so whether it still "does
not fix the thing it looks like it fixes" under floating prizes is open rather than
settled.

**Action.** Correct `docs/tier-derivation.md` §4. The blocker is not "`FHE.div` is
scalar-only" — scalar-only is the form we need. The blocker is that *V5's* denominator
is encrypted, and the fix is to choose a different, plaintext denominator.

## 2.2 [R] The canary claim: right conclusion, wrong reason, and "at any price" is false

`README.md:501-509` says V5's auto-tuning "is not something we skipped — it is
unavailable to us at any price."

The conclusion survives. The reasoning does not, in three places:

1. **The contract can count winners even though an observer cannot.** `accrue` already
   computes `ebool won` per tier per user. Accumulating a per-tier count costs one
   `select` plus one `add`, about 188,000 HCU against ~3.95M — roughly **4.8%** — and
   publishing it reuses the `makePubliclyDecryptable` and KMS path `openDraw` and
   `revealDraw` already run. Not "any price"; a known, small price.
2. **Publishing it would not breach the leakage bar.** `docs/leakage.md` §3 already
   accepts an aggregate winner count, and notes the tier composition is *already
   partially derivable* from `delta totalWeight` against prizes 25/5/1.
3. **The real reason is stronger and we do not state it.** `docs/tier-derivation.md` §2
   proves `E[winners of tier t] = 1/k[t]`, distribution-free. The realised count is an
   unbiased estimator of a constant *we chose*, so it carries no information about gas
   prices, yield, or prize adequacy — the three things V5's canary senses. V5's canary
   is not a win counter, it is a **market**: a bot claims a canary prize only when
   `prize > gas`, so the claim count is a revealed-preference oracle on prize economics.
   Removing the claim removed the market, and **the market was the oracle.**

Push-based distribution has no voluntary cost-sensitive action anywhere in it to read.
That is a sharper result than "FHE forbids it", and it is true.

## 2.3 [R] The clamp counter — the one aggregate here that carries real information

`README.md:1034` names the sharpest limitation: when the reserve runs short "nobody can
tell from the outside, including the person it happened to."

`accrue` already holds both `credit` and `funded` from `tryDecrease`. One `select` plus
`add` into a per-draw counter of declined payouts (~188,000 HCU per user), published
alongside `r` and `totalWeight` at the next `openDraw`, makes the silent failure
observable without naming anyone. It discloses *how many* wins paid nothing — no weight,
no odds, no position — strictly narrower than what §8's window solve already recovers.

**Do not instead publish the reserve level.** It is the tempting zero-FHE-cost route and
it is a leak escalation: `reserve_{N+1} = reserve_N + harvest_N - paid_N`, and
`harvest_N` is derivable from public principal x rate x window, so `paid_N` becomes
solvable *every draw* rather than only in quiet windows — and with prizes 25/5/1 the
tier composition follows. Combined with §8 that attributes a win to a person.

## 2.4 [R] "Both systems hold a reserve" is not true

`README.md:1067`: "Both systems can under-pay and both hold a reserve against it."

V5 allocates `reserveShares` out of every contribution and holds it back **in addition
to** tier liquidity. We have one pot that is simultaneously prize liquidity, backstop,
and the keeper's paymaster. The failure modes are not symmetric.

A caution against the obvious fix: splitting `_reserve` into (pot A, backstop B) with a
fallback chain is **arithmetically vacuous** — a clamp occurs iff `credit > A + B`, which
is `credit > S`. Do not build it. The non-vacuous split is the **keeper fee**: a
dedicated fee pot funded by a plaintext fraction of harvest makes keeper payment
independent of prize solvency in both directions. That is V5's `reserveShares` design and
it is worth having.

## 2.5 [R] Keeper incentives sit on the wrong function

V5 pays for both liveness-critical operations by auction. We pay for neither: `openDraw`
and `revealDraw` carry no reward, and `revealDraw` additionally needs a 12-second
off-chain KMS round trip. The only paid path is `accrueMany` — the one that can be
skipped without wedging anything.

A *fractional* auction is genuinely blocked: V5 prices the reward as a fraction of the
reserve, and a bidder must see the reserve to know whether bidding pays. Ours is
encrypted. But a **time-escalating fixed amount** — `reward = min(elapsed x rate, cap)`
in plaintext, paid through the `tryDecrease` `_payKeeper` already performs — works, is
permissionless, costs ~zero FHE, and leaks nothing.

## 2.6 [R] Smaller, real

- **TWAB delegation** (V5's `delegate(vault, to)`) is absent with no reason given. It is
  implementable: V5 runs TWAB on the delegate balance only, so it is one series, which is
  what our `Observation[]` already is. About 2.9M HCU for the three pushes. The
  delegation edge is a public social link but discloses no amount, weight or outcome.
  **Sponsorship is the risky half and should stay unbuilt** — excluding a sponsor's
  weight from the published total makes a lone sponsor's weight recoverable by
  difference.
- **`claim` grows storage forever.** `_drain` sets `_pending[user] = FHE.asEuint64(0)`,
  whose handle is non-zero, so `isInitialized` stays true and every later permissionless
  `claim(victim)` pushes two more observations carrying an encrypted zero. Low severity —
  the caller pays FHE gas and lookups stay O(log n) — but it is unbounded permissionless
  state growth that V5's ring buffer does not have.
- **No shutdown path.** Principal is never trapped, because `withdraw` needs no draw. But
  if every balance leaves, `totalWeight = 0`, nobody can clear a threshold, and harvested
  yield sits in `_reserve` permanently — irreversibly, after `renounceOwnership`. Either
  add a drain, or state the property: *yield entering the reserve can only leave as a
  prize or a keeper fee.*
- **Per-tier TWAB windows** (V5 scores the grand prize over a longer window) are
  implementable at about +57% accrual cost, **and should not be built**: each tier needs
  its own published `totalWeight`, turning one public aggregate per draw into three over
  overlapping windows, which sharply widens the class of windows §8 can solve. Worth
  recording as a considered rejection rather than a silence.

## 2.7 [R] Confirmed impossible — our side is right

- **Prize hooks.** A hook fires immediately before a claim and runs user code. Any
  observable side effect conditioned on winning *is* the disclosure.
- **Fee-from-prize claiming** (V5's VRGDA `Claimer`). The fee transfer's occurrence and
  its plaintext recipient signal a win.
- **Per-event shortfall disclosure** (`ReserveConsumed`). Correct as stated. The
  *aggregate count* is not blocked — see 2.3.
- **Any `if`/`require` on an encrypted outcome.** The `FHE.select`-only pattern in
  `accrue` is the required shape, and the clamp-instead-of-revert decisions follow from
  it.
- **TWAB Rewards, multi-asset pools, and liquidation/TPDA.** The last has a second reason
  worth recording: TPDA price discovery reads plaintext views (`liquidatableBalanceOf`,
  `maxAmountOut`, `computeExactAmountIn`) before swapping. Under FHE those are
  ciphertexts, so a liquidator cannot size or price a swap — it can only guess and be
  clamped. **A confidential yield balance is structurally incompatible with a
  dutch-auction liquidator**, the same root cause as the blocked fractional draw auction.
  That is a genuine "FHE forces a different shape" result and the project currently
  claims none here.

# Part 3 — Platform capability we are not using

The governing fact, which reframes every proposal below:

| site | HCU today | per-tx ceiling | headroom |
|---|---|---|---|
| `accrue` (cold, 3 tiers) | **3,947,224** — 5 per tx | 20,000,000 | ~0 |
| `openDraw` | ~2,190,000 | 20,000,000 | **~17,800,000** |

Anything added to `accrue` costs keeper throughput linearly. Anything added to
`openDraw` is effectively free — once per draw, ~18M spare. **Every worthwhile idea
below lives in `openDraw`.** That is the most useful structural observation in the
audit.

## 3.1 [V] `withdraw` cannot express "take everything out"

```solidity
(ebool within, euint64 decreased) = FHESafeMath.tryDecrease(balance, amount);
euint64 request = FHE.select(within, amount, FHE.asEuint64(0));
```

Ask for more than you hold and you get **zero** — not your balance. The docs frame this
as deliberate-for-privacy, but privacy is not what makes it clamp to zero; the choice of
`tryDecrease` over `min` is. `FHE.min(euint64, euint64)` exists at 219,000 HCU:

```solidity
euint64 request = FHE.min(balance, amount);    // 219,000
euint64 decreased = FHE.sub(balance, request); // 162,000  -> 381,000
```

against the current path's ~424,000. **Cheaper by ~43,000 HCU, identical observable
behaviour, and it makes `withdraw(type(uint64).max)` mean "all of it".**

Today a full exit requires naming the exact balance, which drifts with every `accrue`
because `_drain` folds pending credit in. Getting it wrong moves nothing and succeeds —
silent, and indistinguishable from every other clamp. This is the highest
value-per-line change in the audit.

## 3.2 [R] `FHE.isUserDecryptable` — the test that would have caught `pendingOf`

`bundle/F1-ACL-SWEEP.md` found `pendingOf` unreadable by its own owner by running a live
Sepolia sweep with real keys, and noted that nothing in the test suite catches it
"because every existing check on these handles asserts non-zero rather than decrypting."

`FHE.isUserDecryptable(handle, user, contractAddress)` turns that sweep into a pure
on-chain assertion — no relayer, no keys, no network. One test, over every externally
returned handle, asserting the intended reader is in the ACL. **This is the missing
invariant, and it is a view function.** Ship it with the two-line `_pending` grant fix or
the class recurs.

## 3.3 [R] `confidentialTransferAndCall` — the most valuable unused item in the stack

Zama's own guidance: prefer it over the operator pattern, because it "delivers the tokens
and notifies the recipient in a single transaction without a standing operator
allowance." The ERC-7984 draft on what we currently grant: "An operator may transfer
**any amount** of tokens on behalf of a holder while approved."

We use the operator pattern everywhere, and the SDK sets `until = now + 365 days`.
Switching the deposit path buys three things at once:

1. **No standing allowance** — removes the 365-day unlimited grant per depositor.
2. **`OperatorSet` stops being emitted.** Today it is a durable, publicly queryable
   pre-announcement that an address intends to join the pool, fired one transaction
   *before* the deposit it enables — which widens the observation window §8's attack
   operates in.
3. **It fixes the custody flaw in 0.4.**
   `onConfidentialTransferReceived(operator, from, amount, data)` hands the pool `from`,
   so `confidentialTransferFromAndCall(owner, pool, …)` credits the **owner** while the
   **session key** signs.

**Cost, measured in this repo rather than estimated:** 823,637 gas / 20 FHE ops versus
625,465 / 9 for the current path — **+32%**, because `_transferAndCall` runs a second
`_update` for the refund leg. The spike also already found the trap: the receiver must
grant the token ACL on the `ebool` it returns or the transfer reverts `ACLNotAllowed`.

Recommendation: keep the cheaper `deposit(externalEuint64, …)` for direct EOA depositors
and **add** an `IERC7984Receiver` entry point for the agent layer. 32% on a deposit is a
fair price for removing an unbounded standing allowance and moving custody off a key
documented as designed-to-leak.

## 3.4 [R] A one-bit solvency proof per draw

In `openDraw`, alongside `r` and `total`:

```solidity
ebool solvent = FHE.ge(_reserve, uint64(grandPrize) * COVER);  // 116,000 HCU, scalar
FHE.makePubliclyDecryptable(solvent);
```

Revealed through the `checkSignatures` path already built, as a third handle in the
existing array. **~116,000 HCU per draw. Negligible.**

It discloses exactly one bit — "the reserve covers N grand prizes at this draw" — about
the *pool*, not any participant. It is the only mechanism by which the will-be-paid
claim becomes checkable by someone who does not trust the operator, and it converts the
silent-zero failure from undetectable to pre-announced.

Respect the permanence rule: only ever disclose a **freshly derived** handle, never a
live state variable that will be reused.

## 3.5 [R] Encrypted-noise house weight — the direct attack on our largest open leak

`docs/leakage.md` §8 is unmitigated: with public `Deposited`/`Withdrawn` events and
plaintext timestamps, `totalWeight_n - totalWeight_{n-1}` for a window containing one
balance change recovers that change **exactly**. Demonstrated live on draw 33: 540.000000
cUSDC, cross-checked. This is a per-user balance disclosure, strictly worse than anything
the README defends.

`openDraw` pushes one extra observation onto `_totalObs` carrying a pad:

```solidity
euint64 pad = FHE.randEuint64(PAD_BOUND);   // 24,000 HCU; bound must be a power of 2
```

pushed **after** the snapshot so it accrues over the next window only. Cost: one extra
`_push` (955,032) plus the rand ≈ **0.98M HCU per draw**, inside a function with ~17.8M
spare. Compare the rejected alternative — encrypting `totalWeight` at **8.3x** with a
40% keeper-throughput loss.

The observer now sees `D*dt_user + pad*dt_window`: one equation, two unknowns. The pad's
*distribution* is public; its realisation is not.

**Residual, stated honestly:** in a window with zero user activity the observer reads
`pad*dt` directly and samples the distribution — which is fine, it is already public —
and a deposit much larger than `PAD_BOUND` still stands out. Sizing `PAD_BOUND` above the
typical deposit is the whole design decision.

**What it costs the product**, quantified: expected winners per draw falls from `1/k` to
`(1-f)/k` where `f = E[pad]/totalWeight`. Compensate by scaling `k` down by `(1-f)`. The
pad is a phantom balance backed by nothing, so the pool simply pays slightly fewer
prizes — anonymity bought with expected prize value, priced in one number.
**Auditability is untouched**: `totalWeight` stays public, thresholds still derive from
it, and the ten-second audit still works verbatim.

## 3.6 [R] "Save together" — the feature the name promises and the product lacks

The tempting build is wrong: a `Circle` contract that pools deposits and splits prizes
needs `FHE.div` by an encrypted member count, which 2.1 shows does not exist.

The buildable version is **delegated weight**, on `VotesConfidential`'s audited
machinery — `delegate`, `delegateBySig` under the
`Delegation(address delegatee,uint256 nonce,uint256 expiry)` typehash,
`_moveDelegateVotes` moving an `euint64` between checkpoints without revealing it.
Alice's *weight*, not her principal, accrues to Bob's threshold check. Principal never
moves, so no-loss is untouched, and mutual delegation between two friends is a
two-person syndicate with pooled odds, one payout target, and both principals
independently withdrawable at any time.

Note `CheckpointsConfidential` is **not** directly reusable — it stores a value per key,
not a time-weighted cumulative, so `getPastVotes` is a balance snapshot rather than a
TWAB. Copy the delegation half; keep our own observation series.

Leaks: the delegation graph is plaintext and public. Amounts, weights and results stay
encrypted. That is the same disclosure `session-leakage.md` already accepts for the
recipient allowlist, and a social graph is what a save-with-friends feature is *for*.
**Design note:** scope the typehash to a `drawId` range, or a leaked signature is a
permanent claim on someone's odds. **And add `Delegated` to §8's event filter**, or it
will mis-attribute residuals exactly as the omitted `Claimed` did.

## 3.7 [R] The ACL design is minimal — the remaining errors run the other way

There is **no structural over-granting.** AA1 closed the one real case, and F1 confirmed
by live decryption that the readable handles are readable because of an explicit
`FHE.allow` naming the reader, not by handle collision. Permanence is contained to
exactly two `makePubliclyDecryptable` calls, both on aggregates.

The remaining problems are all *under*-granting: `_pending` (readable by nobody,
including its owner), `_reserve` (a dead getter today, a missing feature tomorrow — see
3.4), and `SteakhouseReplicaSource.principal()/pending()/inVault()` (in the ABI,
decryptable by nobody).

One client-side note: `packages/sdk/src/fhe.ts` calls `generateKeypair()` fresh on every
decrypt, followed by a fresh `signTypedData` — two full keypair + signature + relayer
round trips per send. The frontend does not have this problem because the v3 SDK caches
the permit. A TTL-scoped cache in the node SDK is a pure latency win at no security cost.

# Part 5 — Do not build these

As valuable as the additions. Each was proposed and rejected with a reason, so nobody
re-proposes them in three weeks.

**Leaderboard, rank, percentile, "top N%".** Prohibited by the brief and by the design:
the aggregate reveal discloses *how many* accounts won and never *which*, and any ranking
reconstructs the second from the first.

**A "recent winners" feed, winner ticker, or win badges.** No data source could populate
it honestly — `winningsOf` is a ciphertext readable only by its holder — so it could only
ever be inference or theatre.

**Anything shareable.** No share-my-odds card, no post composer, no copy-my-position, no
QR. `lib/twab.ts` and `Position.tsx` already forbid it in the code, and the correct
implementation is exactly what exists: nothing.

**A "when will you win" countdown.** `Position.tsx` already rejects it with the right
reason — the draw is memoryless, and *"a countdown to a probabilistic event is a lie with
a clock on it."* An expectation is fine; a clock is not.

**A prize-reserve gauge or liquidity meter.** Structurally impossible, not merely
inadvisable: `reserveHandle()`, `principal()` and `pending()` are ciphertexts that F1's
sweep found unreadable by *anyone*, including the operator. The real need behind it —
"did my prize actually get paid?" — is answered from the holder's own side, which is the
only side that can answer it.

**Push notifications / "you won!" alerts.** Requires either the decryption key
(impossible) or a server watching the address — and *whether a notification fired* is
itself the winner signal the whole protocol was restructured to delete.

**Streaks, badges, gamification.** Behavioural signals about a participant, in a product
whose thesis is that participant behaviour carries no signal.

**Fiat conversion.** The underlying is a mock token on Sepolia. A dollar figure would be
the only number on the site that means nothing.

**A prize-history chart.** `tierPrize` is a constant. It would be a chart of a horizontal
line. (This changes if 2.1 ships — then it becomes worth having.)

**An onboarding tour or explainer modal.** The screens already explain themselves at
length, sometimes at too much length. The fix is fewer words in better places, not a
wrapper around the existing ones.

**A vacuous prize/backstop reserve split.** See 2.4 — `credit > A + B` is `credit > S`.

**Encrypted allowlists for circles** (`eaddress` + `FHE.eq` scan). ~2.7M HCU for 20
members, and it buys nothing an off-chain invite signature does not: the joiner's address
is `msg.sender`, public either way. The on-chain list additionally leaks its own size.

**Sealed-bid auction mechanics.** Every worked example in the corpus is built on the
deprecated `DecryptionOracle`. Rebuilding on the current path is possible, but a
sealed-bid auction needs an ordering over encrypted bids — O(n²) comparisons at 152,000
HCU each — and it reintroduces exactly the cross-user aggregation the tiered design
removed.

**Governance / `ERC7984Votes` on a pool token.** The pool issues no token, and no decision
here is both contentious and safe to vote on. The answer to the owner key is
`renounceOwnership`, which is already built.

**Vesting / lock-ups.** Contradicts the core claim: principal withdrawable at any time.

**Encrypting `totalWeight`.** Measured at 8.3x and rejected; the trade has not changed,
and 3.5 achieves more of the same goal for ~5% of the cost while keeping the public
auditability that encrypting it destroys.

**Swapping `checkSignatures` for `isPublicDecryptionResultValid`.** The library warns
against it explicitly — a caller who forgets to `require` the result lets invalid
signatures pass silently.

**`CheckpointsConfidential` for the TWAB.** 4 slots against the hand-roll's 3, no
`euint128` variant, no cumulative. The hand-roll wins on the measurement.

# Part 7 — The two changes that would raise the ceiling

Everything above is repair and addition. These two are the difference between "good
hackathon project" and "obviously serious", and both agents that looked at positioning
converged on them independently.

## 7.1 Promote the window solve from footnote to spine, and make it run live

The honesty claim currently rests on a leak we **closed** (`can_afford`) and a leak we
**inherited** (Zama's lone-depositor batch aggregate). Both are comfortable stories: one
we fixed, one is someone else's.

§8 is neither. Our design, our deployed pool, an exact recovery of a named depositor's
balance change, found by turning our own measurement technique against ourselves —
complete with the near-miss analysis showing why the naive version produces confidently
wrong numbers about real people.

Two things follow. **Fix the four surfaces that still deny it**, or the best work in the
project reads as an unresolved contradiction and the contradiction is what gets reported.
Then **make Break row 4 compute it in the browser against the current draw**, and name
the deltas recoverable right now. A page that finds a real leak in the pool the visitor
is looking at, names it, and quantifies the condition under which it disappears is a
categorically different artifact from a list of four failed attacks — and it is the one
claim on the site nobody can copy in a weekend, because it requires having built the
thing and then measured it in production.

## 7.2 Establish one number of record

The damaging pattern is not any single wrong figure. It is that almost every headline
number exists in two to four versions (4.2), so a reader cannot tell which was measured —

## Method, and what this audit is not

Four agents read in parallel with no shared context, each given the hard constraints
verbatim (nothing shareable, nothing derived leaving the browser, no leaderboard or
prediction, `totalWeight` public by design) and told that a recommendation violating them
is a failed recommendation.

Findings marked **[V]** were re-checked here — contract source, live chain reads, greps,
and the pinned library. Findings marked **[R]** are cited and plausible and were not
independently re-run; treat them as leads with addresses, not as verdicts. One **[D]**
disagreement is written out rather than smoothed, because the resolution — *V5's literal
mechanism is not expressible, a plaintext-divisor variant is* — is more useful than either
agent's version alone.

Nothing here is a code review. No agent was asked about style, structure, or refactoring,
and none of the above is a request to rewrite working code. Where the repo already
anticipates an objection, the audit says so and moves on; §4.3 exists so that the ratio of
criticism to credit is not mistaken for the ratio of what is wrong to what is right.
