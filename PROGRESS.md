## Task 0 — the gate

Resampled at **n = 180**, 60 per path, after the n = 20 run was correctly called underpowered.

```
path             n      891568     891572   low-rate
success         60          18         42      30.0%
over-budget     60          19         41      31.7%
short-balance   60          16         44      26.7%

chi-square 0.374 on 2 df (critical 5.991 at p=0.05), p = 0.83
mutual information path <-> gas : 0.00151 bits per observation
                                  (Miller-Madow floor at this N is 0.00801 bits)

distinct FHE op sequences : 1   FheAdd x2 FheGe x2 FheIfThenElse x4 FheSub x3 TrivialEncrypt x2
distinct HCU values       : 1   1,334,064
```

The n = 20 run showed 45% / 30% / 20% — a visible trend, and chi-square 2.927. At 60 per path it collapses to 30.0% / 31.7% / 26.7%. **The design is powered to ±13 points, which is exactly the spread the small run appeared to show, so this is a detection failure of a real effect rather than a shrug.** The measured mutual information is now a fifth of the noise floor for the sample size, so the bias-corrected estimate is negative.

Criterion (b) is recorded in `docs/step2-notes.md` as the accepted gate and enforced by `spikes/sepolia-equality.ts`. The residual is bounded in `docs/leakage.md` §3, which also states what n = 180 cannot rule out: a genuine skew below ±13 points. A ±3 point skew would need on the order of 3,000 samples; the console's default cap of 50 gives one session enough power to see only ±24 points or more.

Two things had to be built to get here that were not in the brief:

- **A single-path control**, because proving gas is not a _deterministic_ function of the path is not the same as proving it is _independent_ of it. Ten sends on one fixed path produced both values; the three-path distribution run is what actually closes it.
- **Transient-failure retry.** The first 60-sample run died on sample 5 with `UND_ERR_CONNECT_TIMEOUT` from the Zama relayer. Not a defect in anything under test, but a harness that dies produces no measurement — and, more to the point, a session client that dies on one relayer timeout is unusable. `withRetry` in `spikes/_shared.ts` retries transport failures only; a revert or a failed assertion still surfaces immediately.

## Decision log

### D1 — ethers, not viem. This reverses `docs/step3-sdk-api.md`.

The earlier recommendation argued viem on its `Account` abstraction, first-class EIP-5792, and library ergonomics. §5.1 of the brief changes the weighting decisively: **both keys are generated by the MCP and stay on the machine — no MetaMask, no extension, no browser wallet.** EIP-5792 exists to batch through a browser wallet, so viem's main advantage does not apply to the product's own path.

Against that, _fail fast on load-bearing assumptions_ cuts the other way: every verified thing in this repo — spikes, contract tests, all 82 gate transactions — runs on ethers, and the relayer SDK integration is proven with it. Choosing viem meant building on an unproven integration to gain an advantage the product does not use. `@fhevm/hardhat-plugin` also peer-requires `ethers ^6.16`, so viem would put two web3 libraries in one repo.

EIP-5792 is still implemented for SDK consumers who _do_ have a browser wallet, via `wallet_getCapabilities` and `wallet_sendCalls` with a sequential fallback. About thirty lines; no viem needed.

### D2 — amounts are opaque by construction, not by convention

`AmountRef` has no numeric field, and its resolver lives in a module-private `WeakMap` rather than on the instance — so a plaintext cannot be reached by reading a property, spreading the object, or JSON round-tripping it. `toString` and `toJSON` emit `AmountRef(budget:0x8ea53303…)`, so an accidental template interpolation cannot leak a value. `revealAmount` is the only path to a `bigint`, is named for what it does, and takes a `reason`.

### D3 — two privacy tiers are two types, not a flag

`SpendOnlySession` has no `balance()`. `BalanceVisibleSession` does. A reference amount therefore fails to _compile_ on a session with no ACL delegation. A runtime guard exists too, for JavaScript callers.

### D4 — Web3 Secret Storage v3, not EIP-2335

The brief asked for EIP-2335. EIP-2335 is the eth2 keystore and specifies BLS12-381 secret keys; a session key here is a secp256k1 EOA key, for which the corresponding standard is Web3 Secret Storage v3 — what ethers reads and writes natively, scrypt-based, openable by every EVM tool. Using it means not hand-rolling key derivation, which is the part of that file where a mistake would be worst. Recorded as a deliberate substitution rather than a silent one.

Both keystores generate from raw entropy rather than `createRandom()`, so **no mnemonic is ever derived, held, or written**. The brief is explicit that no seed phrase is shown; this makes it impossible rather than merely unshown.

### D5 — the low-level MCP `Server`, not `McpServer.registerTool`

`registerTool` infers each handler's argument type from a zod shape. That mapped type is deep enough that any schema containing an **array** exhausts TypeScript's instantiation budget (TS2589), and nesting a `z.object` exhausts the compiler's heap outright (exit 134). Six variations were tried — hoisted shapes, `ZodRawShape` widening, pinned generics, an explicit `ToolCallback` annotation, a whole `z.object` as the schema, and dropping `exactOptionalPropertyTypes`. None fixed it; the last two made it worse.

The alternative was contorting the tool schemas to keep an inference engine happy — no arrays in tools that fundamentally take lists — which is the tail wagging the dog. So the schemas are JSON Schema, written by hand, validated with zod explicitly. More code, better control: the exact JSON the model sees lives in one place next to the prose explaining it.

The hazard of hand-written schemas is drift between the schema and the validator. `test/mcp.ts` asserts that every advertised property is required and that a payload built from each schema's own properties validates.

### D6 — `closeSession` does not clear the operator grant, and `revoke_all` says so

`token.setOperator(module, expiry)` lives on the token and expires independently. Closing a session leaves it standing — harmless, because the module has no live session to act under, but a user told "revoked" would reasonably assume otherwise. The tool result names it explicitly rather than letting the word "revoke" over-promise.

## Product gaps found

Standing order: report gaps, not just bugs.

### G1 — "one signature" is one vault unlock, not one EIP-5792 batch

§4 asks for a batched owner operation via EIP-5792; §5.1 specifies both keys are local. These describe different worlds. With no browser wallet there is nothing for `wallet_sendCalls` to batch through: the vault key signs `setOperator`, `openSession` and optionally `delegateForUserDecryption` in sequence, locally, after one unlock.

That is still a true and strong claim — the user authorises once — but it is a _different_ claim, and the README and the console counter must make the true one. `OpenSessionResult.ownerAuthorisations` reports what actually happened rather than what was hoped for, and it is 1 on both paths.

### G2 — `wrap` needs the vault, which §5.3 did not say

The tool list puts `wrap(token, amount)` alongside the session-key tools, but `ERC7984ERC20Wrapper.wrap(address,uint256)` takes a **plaintext** ERC-20 amount and moves a public balance the owner holds. It is `approve` plus `wrap`, signed by the vault key. Implemented as an unlock-requiring tool, and it increments the unlock counter — which is the honest thing for the counter to do.

### G3 — the transfer cap is not a tool argument

§5.3's `open_session` signature has five parameters and no `maxTxCount`. The contract enforces a cap and the SDK exposes it, but a chat client cannot set one. Left as the brief specifies; `session_status` reports the cap, and `docs/leakage.md` §3 explains why the cap is worth setting — it bounds an observer's sample count. Worth adding to the console rather than to the tool surface.

### G5 — the SDK generated a session key it could not pay for

Found by its own integration test, which is the point of writing one.

`openSession` created a session key and returned a working session object, but never funded it. The session key sends its own transactions — that is what makes it a session key rather than a signature scheme — so the first `send` failed with `insufficient funds for gas * price + value: have 0`, minutes later, from inside ethers.

The funding logic existed, but in the wrong layer: the MCP tool did it, so anyone using the SDK directly inherited the footgun. It now lives in `GhostKeyClient.openSession`, which is the only moment the owner is authorised anyway, with `DEFAULT_SESSION_GAS` at 0.02 ETH and `gasForSessionKey: 0n` for callers who want to handle it themselves. `OpenSessionResult.gasForwarded` reports what actually moved.

### G4 — biometric unlock is not implemented

§5.2's preference order is keychain-with-biometric, then a console click, then a terminal passphrase. A real Touch ID / Windows Hello prompt needs a native module per platform. What is implemented is key material at rest under the OS keychain plus a local human action — the second item. `docs/leakage.md` §5 says so rather than implying the first.

### G6 — every session costs the vault 0.02 ETH, and nothing gives it back

Found the same way as G5: the integration suite ran out of gas partway through its
second session. Not a bug — the arithmetic is exactly what it should be — but a
product fact nobody had written down.

The session key sends its own transactions, so the vault forwards
`DEFAULT_SESSION_GAS` (0.02 ETH) at every open. Opening N sessions costs N x 0.02,
and **closing a session does not reclaim the remainder**: the leftover gas stays on
a key that is now permanently unusable, since session keys are single-use by
design. A user who opens a session a day leaks gas at a steady rate for no benefit.

Two ways to fix it, neither done here because both change behaviour rather than
correct a defect:

- sweep the session key's remaining balance back to the vault inside `closeSession`,
  which costs one extra transaction and needs the session key to sign it — it can,
  since it can already close;
- forward less and top up on demand, which trades a smaller float for a failure
  mode in the middle of a send.

The first is better. Recorded for step 5 rather than decided unilaterally, because
it adds a transaction to a flow whose whole claim is about how few there are.

## Adversarial passes

_Who else can call this, with what inputs, and what do they get?_

### The console

- **Another local process.** Every request needs a one-time token minted at startup and never written to disk. Tested: a request without it gets 403.
- **A web page in the user's browser.** The token is in the URL the MCP prints to stderr; a page that does not have it cannot read state or resolve a prompt. CSP is `default-src 'none'` with no remote origins, and `frame-ancestors 'none'`.
- **An unattended console.** A prompt that is never answered resolves as **denied**, not approved. Tested. The failure mode of nobody watching must be that nothing happens.
- **A giant request body.** Capped at 64 KB.

### The vault

- **The model.** It cannot click a button and it cannot answer the terminal: stdin belongs to the MCP transport, and the terminal fallback reads from the TTY. There is no tool that takes a passphrase, so there is no path from a conversation to an unlock.
- **`--dev-unlock` on mainnet.** Refused, and the check is on the chain id at unlock time rather than at construction, so a provider swapped after startup cannot slip past it. Tested, including the case where the vault exists and is loadable — so the test would fail if the gate were merely ordered after the load.

### The session key, if leaked

- Cannot exceed the encrypted budget: enforced homomorphically, and an over-budget request silently moves zero.
- Cannot send outside the allowlist: plaintext check in the contract.
- Cannot widen the allowlist: `addRecipient` is owner-only.
- Cannot call an arbitrary contract: `send` refuses a token with no budget, so a compromised key cannot use the module to grant transient ACL access to an address of its choosing.
- **Can** close the session and remove recipients. Deliberate — a client that detects something wrong must be able to narrow itself without the vault.

### Chain-sourced text

- Token names, symbols and metadata are sanitised before they reach the model: C0/C1 controls, zero-width characters and bidirectional overrides stripped, length capped, injection-shaped text flagged rather than silently passed. Tested against right-to-left override, zero-width space, and four injection patterns.
- The defence in depth matters more than the sanitiser: an injection that succeeds _completely_ still cannot move value to an address the owner did not name, or beyond the budget the owner set.

### The SDK's amount type

- `${ref}` → `AmountRef(budget:0x8ea53303…)`; `JSON.stringify({ref})` contains no number. Asserted in the Sepolia suite against a real handle.
- The resolver is in a `WeakMap`, so spreading or cloning the object drops it rather than carrying a plaintext along.

## Judgement calls close to a stop condition

None met §2. These were the closest.

1. **The relayer timeout that killed the first 60-sample run.** Arguably §2.5 — "a dependency behaves differently from what the earlier documents recorded". Judged transient infrastructure rather than a behaviour change: `findings.md` never claimed the relayer was reliable, and a retry recovered it. Recorded as a real product requirement instead, since the SDK needs the same treatment.

2. **The 4 gas.** Under a strict reading of §2.1 this was a stop — the gate's literal criterion failed. It _was_ stopped on, reported, diagnosed to a single call in a third-party contract, and the criterion revision was put to the reviewer rather than applied. Task 0 then confirmed the distributions are indistinguishable. Noted because the boundary between "diagnose it" and "work around it" is exactly where a standing order gets abused, and this run went to the reviewer.

3. **The MCP SDK's type inference.** Six failed attempts before switching to the low-level API. Not a stop condition — the dependency works, only its TypeScript surface is hostile — but it consumed real time and the resolution changed the architecture of one file. Recorded as D5 rather than buried.

4. **`--dev-unlock` exists at all.** It skips the human authorisation step, which is §2.3-adjacent. Kept because the brief asks for it explicitly, hard-gated to Sepolia, and asserted in a test that would fail if the gate were removed or reordered.
